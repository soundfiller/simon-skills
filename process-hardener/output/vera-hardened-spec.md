> Generated by process-hardener v1.0 · 2026-05-30

## 1. Process Overview

```
Archiv (research agent)
  │
  ├── brief.md (verified numbers, sources, key claims)
  ├── slide-outline.md (slide-by-slide with content assignments)
  │
  ▼
Vera (presentation agent)
  │
  ├── §1 Research Handoff (SENSE)    — verify brief, flag gaps, map to templates
  ├── §2 Consulting Narrative (DECIDE) — action titles, pyramid principle, exhibit cookbook
  ├── §3 Deck Building (ORCHESTRATE)  — pptxgenjs build, 25 templates, Hugiin V3 design system
  ├── §4 Quality Gates (GOVERN)       — pre-gate + post-gate, never optional
  ├── §5 Modification (MAINTAIN)      — patch script, rebuild, re-audit
  └── §6 Learning Feed (LEARN)        — deck-memory.jsonl, failure-log.md, style-patterns.md
  │
  ▼
Måns (human reviewer)
  └── Reviews deck, provides feedback → Vera §5 (Modification)
```

**Sub-agent routing:**
| Task | Model | Role |
|------|-------|------|
| Strategy, storyline, gates | Vera (DeepSeek Pro) | Judgment |
| Slide content, chart data | GPT-5-mini | Fast assembly |
| Fact verification | Sonnet | Careful cross-ref |
| Mechanical fixes | Qwen | Cheap, focused |

## 2. Hardening Summary

Vera's process is unusually mature for an MVP — quality gates exist, failure logging is operational, and the design system is fully tokenized. This is not hardening from zero. It's hardening from "works well until it doesn't" to "survives operator absence, volume spikes, and adversarial inputs."

**What's strong:** Pre/post gates, failure log, design system tokens, red lines, the Source Classification Check (post-F001 fix).

**What needs hardening:** Sub-agent resilience, gate independence, version control, parallel builds, testing, rollback, runbook.

**High-priority finds:**
1. **No retry/fallback for sub-agent failures** — if GPT-5-mini or Sonnet don't respond, the build silently hangs or produces garbage
2. **Gate runner = gate subject** — Vera both builds the deck and judges it. No independent verification.
3. **No version control on build scripts** — "modify script, rebuild" but the script isn't versioned. One bad edit = no undo.
4. **No test suite** — design system changes are deployed untested. A CSS token change could break every slide.
5. **No runbook** — if Måns is unavailable and a build fails, nobody knows what to do.

## 3. Dimension Specifications

### Dimension 1: Error Handling & Resilience

**Gap Analysis:**
- Sub-agent calls (GPT-5-mini, Sonnet, Qwen) have no retry logic, no timeout, no fallback path
- pptxgenjs build failures have no recovery path — if the script crashes mid-build, the .pptx is corrupt
- Brief verification (§1) identifies gaps but there's no SLA for Archiv to respond — Vera waits indefinitely
- Design system file reads (`colors_and_type.css`, template HTML files) can fail silently
- The "PASS WITH WARNINGS" gate outcome has no guidance on when warnings become failures

**Hardening Requirements:**

1.1 **Sub-agent call wrapper.** Wrap every sub-agent invocation with:
- Timeout: 120s for GPT-5-mini (content assembly), 180s for Sonnet (fact verification), 60s for Qwen (mechanical fix)
- Retry: 2 attempts with 30s exponential backoff (30s, 90s) on transient failures
- Fallback: If GPT-5-mini fails after retries → Vera does content assembly inline (degraded mode, flag in gate). If Sonnet fails → build continues with `FACT_CHECK_SKIPPED` warnings, every unsourced claim flagged. If Qwen fails → mechanical fixes queued for post-build.

1.2 **Build crash recovery.** Wrap pptxgenjs execution:
- Save partial .pptx at slide boundaries (every 5 slides)
- On crash: log crash point with slide number and error, offer to rebuild from crash point
- Build script must produce a valid .pptx even if truncated (graceful degradation)

1.3 **Brief SLA.** After flagging gaps to Archiv:
- If no response in 60 minutes: proceed with flagged gaps, mark deck `BRIEF_INCOMPLETE`
- If 3 consecutive builds have `BRIEF_INCOMPLETE`: escalate to Måns

1.4 **File integrity checks.** Before build:
- Verify all design system files are readable and parse correctly
- Verify slide template HTML files exist for all mapped template types
- On failure: halt build with specific missing-file error, do not proceed

1.5 **Warning escalation.** Define thresholds:
- 3+ warnings → treated as FAIL-CORRECTABLE
- Same warning type recurring across 3 builds → treated as FAIL-BLOCKING, requires root cause fix

### Dimension 2: Edge Cases & Boundary Conditions

**Gap Analysis:**
- No handling for empty/missing brief.md or slide-outline.md
- No handling for non-Hugiin branding (what if Måns wants an Adler Pelzer deck?)
- No handling for decks that don't fit the 25-template catalog
- No handling for extremely large decks (50+ slides)
- No handling for concurrent builds (two decks requested simultaneously)
- Dark/light rhythm assumption breaks on mono-section decks (the Autins build had "consecutive light blocks within thematic sections" — flagged as warning, not resolved)

**Hardening Requirements:**

2.1 **Input validation.**
- Empty brief.md → halt, request brief from Archiv/Måns
- Missing slide-outline.md → halt, request outline
- Brief with zero sourced claims → flag as `BRIEF_UNSOURCED`, require Måns confirmation before proceeding
- Slide count outside 5-50 range → warn (large decks strain sub-agent pipeline), proceed with chunked build

2.2 **Multi-client branding.** The design system currently assumes Hugiin. Add a client override:
```yaml
# In brief.md or a client-config.json
client_name: "Adler Pelzer Group"
logo_path: "skills/vera/client-logos/adler-pelzer.svg"
primary_color: "#003A70"  # overrides iris
```
Default to Hugiin. Support overrides for: logo, primary accent color, surface color (linen or client preference). Document which overrides are safe vs. which break the design system.

2.3 **Template mapping failures.** If a slide in the outline doesn't map to any of the 25 templates:
- Log the unmapped slide
- Offer nearest-neighbor template suggestion
- Flag in pre-gate as `TEMPLATE_MISMATCH`
- If >20% of slides unmapped: halt, request outline revision

2.4 **Large deck handling.** For decks >30 slides:
- Chunk build into batches of 10 slides
- Run fact verification in parallel per batch
- Assemble final .pptx from batch outputs
- Warn on build time >300s

2.5 **Concurrency control.** If a second build is requested while one is running:
- Queue the second build, report position in queue
- Do NOT run parallel builds unless explicitly requested
- If parallel: isolate build directories, prevent file collisions

2.6 **Dark/light rhythm.** For mono-section decks (all analysis, no dividers):
- Allow consecutive light slides within a thematic block
- Flag in pre-gate as intentional, not a warning
- Insert a dark pull-quote or KPI dashboard slide every 8-10 slides as visual breathing point

### Dimension 3: Monitoring & Observability

**Gap Analysis:**
- `deck-memory.jsonl` exists but is never analyzed — it's a log, not a monitoring system
- No build success rate metric
- No gate pass/fail rate metric
- No rework cycle tracking
- No alerting when builds fail
- Mean time to detect a bad build: when Måns notices (could be hours or days)

**Hardening Requirements:**

3.1 **Build health dashboard.** Parse deck-memory.jsonl and surface:
- Build success rate (last 30 days)
- Gate pass rate (PASS vs PASS_WARNINGS vs FAIL)
- Average rework cycles per deck
- Average build time
- Most common gate failures
- Trend: is quality improving or degrading?

3.2 **Alerting thresholds.** Automatic alerts when:
- Gate result is FAIL-BLOCKING → immediate notification to Måns
- 3 consecutive builds with PASS_WARNINGS → flag for review
- Build time exceeds 300% of average → performance investigation
- Fact verification finds >10% of claims unsourced → brief quality alert
- New failure type appears in failure-log → alert (unknown unknowns)

3.3 **Correlation ID per build.** Every build gets a UUID. Logged in deck-memory.jsonl. Every sub-agent call, gate check, file read, and modification traces to this UUID. When something breaks, trace the full execution chain.

3.4 **Observability gaps.** Add logging for:
- Sub-agent call latency (per model)
- Template mapping success rate
- Design system file parse time
- Brief completeness score (0-100)

### Dimension 5: Validation & Quality Gates

**Gap Analysis:**
- Gates exist and are well-designed — the strongest dimension. But:
- Gate runner = gate subject. Vera both builds and judges the deck
- Hallucination scan is 20% spot check — insufficient for board-level decks where one wrong number is catastrophic
- No automated gate evidence — gates rely on Vera's judgment, not automated checks
- Post-gate checks are described but not enforceable (e.g., "color audit" — how is this verified?)

**Hardening Requirements:**

5.1 **Independent gate pass.** After Vera builds:
- Spawn a separate, stateless sub-agent (no build context) to run the post-gate
- The gate agent receives only: the .pptx file, the brief.md, and the gate checklist
- Gate agent cannot modify the build — it only judges
- This prevents the "I built it so it must be good" bias

5.2 **Automated gate checks.** Where possible, replace manual checks with automated ones:
- Color audit → script that extracts all colors from .pptx XML and validates against design system palette
- Font audit → script that extracts all font references and validates Arial/Consolas only
- Source verification → script that counts source lines on chart slides, compares to slide count
- Structural check → script that validates dark/light alternating pattern
- These scripts are cheap, fast, and never skip checks.

5.3 **Hallucination scan calibration.** Raise from 20% spot check:
- For decks ≤20 slides: 100% of numerical claims verified
- For decks 21-40 slides: 50% random sample + all KPI slides
- For decks >40 slides: 25% random sample + all KPI slides + all recommendation slides
- Any verification failure → full 100% scan

5.4 **Gate evidence package.** Every gate run produces a gate report:
```json
{
  "build_id": "uuid",
  "gate_type": "post-gate",
  "timestamp": "ISO-8601",
  "checks": [
    {"check": "color_audit", "result": "PASS", "evidence": "0 violations in 847 color references"},
    {"check": "font_audit", "result": "PASS", "evidence": "Arial: 234 refs, Consolas: 56 refs"},
    {"check": "source_verification", "result": "PASS", "evidence": "12/12 chart slides have source lines"},
    {"check": "hallucination_scan", "result": "PASS", "evidence": "18/18 numbers verified (100% sample)"}
  ],
  "result": "PASS"
}
```
Gate reports are append-only and traceable.

5.5 **Gate calibration.** Review gate outcomes monthly:
- If PASS_WARNINGS rate >30% → gate is too strict or too lenient, calibrate
- If FAIL-BLOCKING rate = 0% over 30 builds → gate might be missing something
- If same check always passes → it's non-discriminating, remove or harden it

### Dimension 6: Rollback & Recovery

**Gap Analysis:**
- "Modify script, rebuild" is the stated recovery — good principle, but:
- Build scripts are not versioned — one bad edit, no undo
- Successful .pptx files are not backed up before rebuild
- No isolation between "in-progress" and "last-known-good" state
- No git integration for build scripts
- deck-memory.jsonl is append-only but has no recovery if corrupted

**Hardening Requirements:**

6.1 **Version control for everything.** Initialize a git repo for the skills directory:
- `skills/vera/` under version control
- `skills/hugiin-design/` under version control
- Every build script change committed with message: `deck: <deck_id> — <change description>`
- Tag successful builds: `git tag build/<deck_id>/PASS`
- This gives: diff history, rollback, blame, audit trail

6.2 **Build isolation.** Per build:
- Create a `builds/<deck_id>/` directory
- Copy the build script there (isolated from concurrent edits)
- Build output goes to `builds/<deck_id>/output.pptx`
- Gate report goes to `builds/<deck_id>/gate-report.json`
- On PASS: copy to `decks/<deck_id>/final.pptx` (the canonical output)
- Never overwrite `decks/<deck_id>/` — version with timestamp if rebuilt

6.3 **Rollback procedure.** 
- To revert a deck: `git checkout <tag>`, rebuild from tagged script
- To recover corrupted deck-memory.jsonl: restore from git history (the file is append-only — no merges)
- To recover from a bad design system change: `git revert` the token change, rebuild all affected decks

6.4 **Backup strategy.**
- `decks/` directory backed up (it's the canonical output)
- `.jsonl` files are append-only text — easy to backup, easy to restore
- Git history IS the backup for scripts and config

### Dimension 7: Scaling & Performance

**Gap Analysis:**
- Build time not tracked (deck-memory.jsonl shows `build_time_seconds: 0` for both builds)
- No parallel build support
- Sub-agent pipeline is sequential by design — fact verification waits for content assembly
- Large decks (>30 slides) have no special handling
- Design system file reads happen at build time — no caching

**Hardening Requirements:**

7.1 **Build time tracking.** 
- Start timer at brief verification, stop at gate pass
- Log to deck-memory.jsonl
- Track per-stage timing: verify brief, narrative design, content assembly, fact verification, PPTX generation, post-gate
- Baseline from first 10 builds, then alert on deviation >2σ

7.2 **Pipeline parallelization.**
- Content assembly (GPT-5-mini) and fact verification (Sonnet) can run in parallel on different slides
- Split slide list into batches, dispatch to sub-agents concurrently
- Merge results before PPTX generation
- Reduces build time by ~40% on decks >15 slides

7.3 **Caching strategy.**
- Design system files (CSS, HTML templates) → cache in memory on first read, invalidate on file change
- Style patterns → cache Måns preferences, re-read only on update
- Brief verification results → cache if brief hasn't changed since last build

7.4 **Load handling.**
- Priority queue for builds (Måns-requested > automated > experimental)
- Maximum 2 concurrent builds (prevents API rate limiting)
- Build timeout: 600s (10 min) for decks ≤20 slides, 1200s for larger decks
- On timeout: deliver partial output with warning, do not silently fail

### Dimension 8: Compliance & Governance

**Gap Analysis:**
- Source Classification Check exists (post-F001) — good
- But: no client data isolation (what if two clients' briefs mix?)
- No data retention policy for briefs, builds, or outputs
- No access control — anyone with Vera access can build any client's deck
- No audit trail for who requested what deck
- Copyright/likeness risk for benchmark aesthetic (McKinsey, BCG look)

**Hardening Requirements:**

8.1 **Client data isolation.**
- Per-client directories: `clients/<client_name>/briefs/`, `clients/<client_name>/decks/`
- Never cross-reference data between clients without explicit approval
- Brief.md tagged with `client: <name>` and `confidentiality: <level>`

8.2 **Confidentiality levels.**
| Level | Definition | Handling |
|-------|-----------|----------|
| PUBLIC | Intended for public release | No restrictions |
| CONFIDENTIAL | Internal / client-only | Client-isolated directory |
| RESTRICTED | Board-level / M&A / strategic | Build-only, no persistence of intermediate data, manual Måns approval per build |

8.3 **Data retention.**
- Briefs: retain indefinitely (git versioned)
- Build scripts: retain indefinitely (git versioned)
- Intermediate build artifacts: delete after gate PASS, retain 30 days on gate FAIL
- Final .pptx: retain indefinitely in client directory
- Gate reports: retain indefinitely

8.4 **Access control.** Vera's AGENTS.md already defines "ask first" for external audiences. Formalize:
- Internal Hugiin decks → Vera can build autonomously
- External client decks → Måns must approve the brief before build
- M&A / board decks → every build step requires Måns confirmation

8.5 **Audit trail.** Every deck has:
- Who requested it (Måns, Archiv, other)
- When built, by which model configuration
- Gate results with evidence
- Who approved final output
- All retrievable from deck-memory.jsonl + git history

### Dimension 9: Stakeholder Handoffs & Communication

**Gap Analysis:**
- Archiv → Vera pipeline is defined but handoff criteria are fuzzy
- Måns review loop exists but is informal — no structured feedback mechanism
- No status communication during long builds
- No notification when a deck is ready for review
- No defined feedback loop from Måns back to the learning system

**Hardening Requirements:**

9.1 **Archiv → Vera handoff protocol.**
Archiv must provide:
- `brief.md` with completeness score (0-100). Below 70 → rejected, sent back.
- `slide-outline.md` with template assignments. Unmapped slides → rejected.
- `client_config.json` if non-Hugiin branding.
- Vera acknowledges receipt and estimated build time.

9.2 **Build status communication.**
During build:
- "Verifying brief..." (30s)
- "Building narrative structure..." (60s)
- "Assembling content (slides 1-10 of 18)..." (2-5 min)
- "Fact verification in progress..." (3-8 min)
- "Generating PPTX..." (30s)
- "Running post-gate..." (30s)
- "Build complete. Gate: PASS. Ready for review."

9.3 **Måns feedback loop.** After Måns reviews:
- Structured feedback format: slide number, issue type (content/design/data), description, severity (must-fix/nice-to-have)
- Vera acknowledges each feedback item
- Modification cycle tracked (rework_cycles in deck-memory.jsonl)
- Pattern extraction: if same feedback appears 3+ times, update style-patterns.md

9.4 **Review notification.**
- On gate PASS: notify Måns with build summary (slide count, gate result, top findings, link to deck)
- On gate FAIL-CORRECTABLE: notify with prioritized fix list
- On gate FAIL-BLOCKING: immediate alert to Måns

### Dimension 10: Testing & Verification

**Gap Analysis:**
- No test suite exists — the biggest gap in the current process
- Design system changes deploy untested
- New slide templates are added without regression testing
- No way to verify the build pipeline works before building a real deck

**Hardening Requirements:**

10.1 **Design system regression suite.** Create a test deck that exercises every component:
- One slide per template (all 25 types)
- Every color in the palette
- Every typography style (all 11 sizes)
- Every chart type
- Every component: cards, callouts, grids, bars, 2×2, heat maps, tables, roadmaps, chevrons, org charts
- Build this test deck on every design system change
- Automated diff against previous build: pixel comparison of rendered slides
- Fail if any visual regression detected

10.2 **Build pipeline smoke test.** Before every real build, run:
- Mini-deck: 3 slides (cover, KPI dashboard, closing) using test brief
- Validate: .pptx opens without errors, colors match palette, fonts are Arial/Consolas
- If smoke test fails → do not proceed with real build, alert operator
- Smoke test runs in <60s

10.3 **Brief validity test.** Before accepting a brief from Archiv:
- Schema validation: all required fields present
- Source verification: at least 80% of claims have `source:` annotations
- Number consistency: no contradictory claims within the brief
- Template coverage: ≥90% of outline slides mapped to valid templates

10.4 **Gate regression test.** Periodically (weekly):
- Feed a known-bad deck through the post-gate
- Verify gate catches injected errors:
  - Wrong color in a chart
  - Missing source citation
  - Passive-voice action title
  - Em dash in body copy
- If gate misses an injected error → gate is broken, fix immediately

10.5 **Chaos engineering (light).**
- Simulate sub-agent failure: build with one model unavailable → verify graceful degradation
- Simulate file corruption: build with truncated brief → verify halt behavior
- Simulate template deletion: build with missing template → verify error message quality
- Run quarterly

## 5. Process Runbook

### Normal Operations

**Requesting a deck:**
1. Archiv delivers `brief.md` + `slide-outline.md` to Vera
2. Vera runs brief validity test (Dimension 10.3)
3. If valid: Vera acknowledges, provides estimated build time
4. Vera builds deck through §1-§4
5. Post-gate runs independently (Dimension 5.1)
6. Gate result + summary sent to Måns
7. PASS → deck ready. FAIL → fix list sent.

**Reviewing a deck:**
1. Måns opens .pptx + gate report
2. Provides structured feedback per slide (Dimension 9.3)
3. Vera runs modification cycle (§5)
4. Re-gate
5. Repeat until PASS

### Common Failures

**"Brief is incomplete" (below 70% completeness score)**
→ Reject brief. Send back to Archiv with specific gaps listed.
→ If Archiv doesn't respond in 60 min: escalate to Måns.

**"Template mapping failed" (>20% of slides unmapped)**
→ Halt build. List unmapped slides with nearest-neighbor suggestions.
→ Måns or Archiv revises outline.

**"Fact verification found issues" (>10% of claims unverified)**
→ Build continues with `FACT_CHECK_WARNINGS`.
→ Every unverified claim flagged in the deck footer as `[UNVERIFIED]`.
→ Måns decides: ship with warnings or hold for verification.

**"Build script crashed" (pptxgenjs error)**
→ Check crash point in log. Save partial output.
→ Fix script. Rebuild from crash point or full rebuild.
→ If same script crashes twice: full rebuild from template.

**"Sub-agent unavailable" (GPT-5-mini/Sonnet/Qwen timeout)**
→ Retry with backoff (Dimension 1.1).
→ If still unavailable after retries: fallback path (Dimension 1.1).
→ Alert Måns that deck was built in degraded mode.

### Escalation

| Level | Who | When |
|-------|-----|------|
| Tier 1 | Vera self-healing | Transient failures (retry succeeds) |
| Tier 2 | Vera notifies Måns | Gate FAIL, degraded mode, unknown error |
| Tier 3 | Måns intervenes | FAIL-BLOCKING, data integrity issue, 3+ consecutive degraded builds |

## 6. Testing Plan

### Smoke Test (before every build)
```
Input: 3-slide mini-brief (cover, KPI, closing)
Expected: Valid .pptx, correct colors, Arial/Consolas fonts
Pass condition: .pptx opens without error, color audit passes, font audit passes
Time: <60s
```

### Design System Regression Test (on any CSS/template change)
```
Input: 25-slide test brief (one per template)
Expected: All components render correctly, no visual regression
Pass condition: Automated diff against baseline screenshots shows 0 differences
Time: 3-5 min
```

### Gate Regression Test (weekly)
```
Input: Known-bad deck with injected errors (wrong color, missing source, passive title, em dash)
Expected: Gate catches all injected errors
Pass condition: 4/4 errors caught
Time: 1 min
```

### Build Pipeline Integration Test (on SKILL.md changes)
```
Input: Real brief from a past successful build
Expected: Identical output to the tagged build
Pass condition: .pptx binary identical (or visually identical per diff)
Time: 5-10 min
```

### Chaos Test (quarterly)
```
Scenario 1: "GPT-5-mini unavailable"
  Expected: Build completes in degraded mode, all flags present, Måns alerted
Scenario 2: "brief.md truncated (missing last 50%)"
  Expected: Build halts, clear error message, specific missing sections listed
Scenario 3: "template 07-Market-Sizing.html deleted"
  Expected: Build halts, specific file path in error, template suggestion offered
```
